## 1 为什么在 SOA / 微服务中通常不推荐长事务，而更常用 Saga？

在分布式系统里，长事务通常意味着：

- 持有资源时间长
- 参与方多
- 跨网络协调
- 回滚链路复杂

这会显著降低系统的吞吐、可用性和恢复能力。

### 为什么长事务问题大

#### 1. 资源长时间占用

例如锁、连接、线程、事务上下文会被长时间占住，容易拖垮系统吞吐。

#### 2. 跨服务 ACID 成本极高

一旦事务跨越多个服务、数据库或队列，就需要协调机制，而这会带来：

- 阻塞
- 单点协调压力
- 故障恢复复杂
- 高延迟

#### 3. 失败后的回滚不再简单

本地数据库事务可以回滚，但跨服务后，很多动作已经对外产生副作用，例如：

- 发券
- 扣库存
- 调用支付
- 发通知

这些不一定能靠数据库 rollback 解决。

### 为什么 Saga 更常见

Saga 的思路是：

> 把一个长业务流程拆成多个本地事务，每步成功后推进下一步；如果某步失败，就执行补偿动作。

### Saga 的优势

- 更适合分布式环境
- 避免长时间锁资源
- 每个服务维护自己的本地事务边界
- 更利于独立扩展和恢复

### 但 Saga 也不是免费午餐

它会引入：

- 补偿逻辑设计复杂
- 最终一致性而非强一致
- 重试、幂等、顺序控制要求更高

### 面试回答要点

> 长事务在分布式系统中代价高，是因为它把锁、协调和失败恢复都跨网络放大了；Saga 更常见，是因为它把问题转成多个本地事务 + 补偿，从而更适合高可用和松耦合架构。

## 2 SOA 和微服务有什么区别？

SOA（Service-Oriented Architecture）和微服务都强调“服务化”，但关注点和落地风格不同。

### SOA 更强调什么

SOA 更偏企业级系统集成，关注：

- 服务复用
- 跨系统集成
- 统一治理
- 异构系统互操作

典型特征包括：

- 服务粒度相对更粗
- 更强调企业范围内共享能力
- 常配合 ESB、SOAP、WSDL 等传统企业集成技术

### 微服务更强调什么

微服务更强调：

- 围绕业务能力拆分
- 独立部署
- 小团队自治
- 去中心化治理
- 快速迭代

典型特征包括：

- 服务更小、更专注
- 更倾向每个服务独立数据存储
- 更常使用 REST、gRPC、消息队列等轻量通信方式

### 核心区别

| 维度 | SOA | 微服务 |
|---|---|---|
| 目标 | 企业级复用与集成 | 快速交付与自治演进 |
| 粒度 | 通常更粗 | 通常更细 |
| 治理方式 | 更集中 | 更去中心化 |
| 通信风格 | 常见 ESB / SOAP | REST / gRPC / Event-driven |
| 团队模型 | 跨部门共享服务 | 小团队 owning 单个服务 |

### 现代现实

今天很多团队提“微服务”，但实际部分能力仍带有 SOA 色彩，例如：

- 企业统一身份服务
- 统一风控服务
- 共享主数据平台

所以两者不是绝对对立，而是有历史继承关系。

### 面试回答要点

> SOA 和微服务都属于服务化架构，但 SOA 更偏企业集成和复用，微服务更偏业务能力拆分、独立部署和团队自治。微服务可以看作在云原生和 DevOps 时代更轻量、更去中心化的一种服务化实践。

## 3 Web 服务如何做版本管理、兼容性治理和破坏性变更处理？

版本管理的目标不是“URL 上写 v2”这么简单，而是：

> 在持续演进服务能力的同时，降低客户端中断风险和迁移成本。

### 常见版本管理方式

#### 1. URI 版本

```text
/api/v1/orders
/api/v2/orders
```

优点：

- 直观
- 文档友好
- 易于对外管理

#### 2. Header / 内容协商版本

适合更严格的协议化治理，但执行门槛更高。

### 更重要的是兼容性治理

#### 优先向后兼容演进

例如优先做：

- 新增可选字段
- 新增端点
- 保留旧字段
- 放宽解析兼容性

#### 明确破坏性变更的定义

例如：

- 删除字段
- 改字段语义
- 收紧校验规则
- 改默认排序或分页行为
- 修改错误码契约

#### 做弃用（Deprecation）管理

- 提前公告
- 提供 sunset 时间
- 标记废弃字段 / 接口
- 给出迁移指南
- 监控旧版本使用情况

### 微服务内部也需要版本治理吗？

需要，只是形式可能不同。

服务间接口可以通过：

- protobuf 演进规则
- schema registry
- contract testing
- backward compatibility tests

来治理，而不一定显式暴露 `v1/v2`。

### 面试回答要点

> 版本治理的关键不是版本号放哪，而是尽量用向后兼容演进减少 breaking change；当确实要做破坏性变更时，要有弃用周期、迁移路径、契约测试和使用监控。

## 4 事务和 Saga 在 SOA / 微服务中有什么区别？

### 事务（Transaction）

传统事务追求：

- 原子性
- 一致性
- 隔离性
- 持久性

在单库、单服务里，它通常是最可靠、最简单的选择。

### Saga

Saga 面向的是跨服务业务流程。它通过：

- 多个本地事务
- 事件或编排驱动
- 失败时执行补偿动作

来实现业务上的最终一致性。

### 本质区别

| 维度 | 传统事务 | Saga |
|---|---|---|
| 一致性 | 更强 | 通常是最终一致 |
| 作用范围 | 单库 / 紧耦合边界内 | 跨服务 / 跨系统 |
| 失败处理 | rollback | compensation |
| 对资源占用 | 可能阻塞 | 通常更松耦合 |
| 复杂度 | 本地较低 | 分布式下更高 |

### 什么时候优先用事务

- 能在单个数据库事务内解决
- 业务强一致要求高
- 没必要为“分布式”而人为拆散边界

### 什么时候用 Saga

- 流程天然跨多个服务
- 每个服务拥有自己的数据
- 可以接受最终一致性
- 需要更高可用性和更松耦合

### 面试回答要点

> 如果能用单库事务解决，通常优先用事务；Saga 是在跨服务边界下，为避免高代价分布式事务而采用的现实折中。它追求的是业务可恢复和最终一致，而不是数据库层面的即时原子提交。

## 5 什么时候微服务会“拆得太细”（too micro）？

当服务拆分带来的协作、网络和运维复杂度，已经超过它带来的自治和演进收益时，就拆得太细了。

### 常见信号

#### 1. 一次改动总要改很多服务

如果一个简单业务变更总要同时改 5-10 个服务，说明边界可能切错了。

#### 2. 服务间同步调用链太长

调用链越长：

- 延迟越高
- 失败传播越严重
- 调试越困难

#### 3. 服务只是数据库表拆分，不是业务能力拆分

如果一个服务只是“用户地址表服务”“用户昵称表服务”这种级别，往往过细了。

#### 4. 团队规模撑不起服务数量

微服务不是靠服务数取胜。一个小团队维护几十个服务，通常会在：

- 监控
- CI/CD
- 安全补丁
- 升级治理

上被拖垮。

#### 5. 大量时间花在平台摩擦上

比如：

- 配置同步
- 调接口排错
- 跨服务联调
- 权限申请
- 协议兼容

### 正确的拆分依据

更好的依据通常是：

- 业务能力边界
- 团队 ownership
- 变化频率差异
- 扩展需求差异

### 面试回答要点

> 微服务“太微”的表现，不是服务数量多本身，而是业务改动跨服务蔓延、同步链路过长、团队负担过重。拆分边界应该围绕业务能力和演进需求，而不是为了追求形式上的细粒度。

## 6 微服务架构的优缺点是什么？

微服务的核心价值在于：

> 把系统拆成围绕业务能力自治演进的服务单元。

### 优点

#### 1. 独立部署

不同服务可以独立发布、回滚和扩缩容。

#### 2. 更贴近业务边界

如果拆分得当，服务边界能更好映射团队和业务能力。

#### 3. 故障隔离更好

单个服务故障不一定拖垮整个系统。

#### 4. 技术演进更灵活

不同服务可以按需采用不同技术，但前提是组织能承受治理成本。

#### 5. 更适合大团队协作

在组织规模较大时，微服务有助于团队自治和并行开发。

### 缺点

#### 1. 分布式复杂度显著增加

包括：

- 网络调用失败
- 超时 / 重试
- 一致性问题
- 分布式 tracing
- 配置治理

#### 2. 运维和平台要求更高

微服务要真正落地，通常需要：

- CI/CD
- 容器平台
- 服务发现
- 监控告警
- 统一日志
- 安全治理

#### 3. 测试更复杂

单元测试不够，还需要：

- contract test
- integration test
- e2e test
- chaos / resilience test

#### 4. 认知负担更高

服务越多，整体系统越难形成统一心智模型。

### 现代结论

微服务不是成熟团队的“默认起点”，而是系统规模、团队规模和交付复杂度达到一定程度后的组织化选择。

### 面试回答要点

> 微服务的优势是自治、独立部署和可扩展，代价是分布式复杂度、平台复杂度和认知负担显著上升。它适合复杂系统和较大团队，但不是所有系统一开始都应该采用的默认架构。
