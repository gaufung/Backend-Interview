## 1 为什么我们需要并发？

首先要区分两个概念：

- **并发（Concurrency）**：多个任务在逻辑上交错推进
- **并行（Parallelism）**：多个任务在物理上同时执行

并发不一定意味着多核同时跑，它也可以是在单核上通过调度器时间片切换来实现。

### 为什么需要并发

并发的价值通常来自三类需求：

#### 1. 提升资源利用率

很多程序并不是一直都在做 CPU 计算，而是会等待：

- 磁盘 I/O
- 网络 I/O
- 锁
- 外部服务响应

如果一个任务阻塞时，系统还能推进其他任务，就能显著提升吞吐量。

#### 2. 改善响应性

例如桌面应用或服务端程序可以同时：

- 接收输入
- 执行业务逻辑
- 后台刷新数据
- 处理定时任务

这使系统不会因为某个慢操作而“卡死”。

#### 3. 利用多核硬件

在计算密集型场景中，多线程 / 多进程 / 并行任务可以更充分利用现代 CPU 的多核能力。

### 后端系统中的典型例子

- Web 服务器同时处理多个请求
- 消息消费者并发处理消息
- 数据流水线并发拉取、解析、写入
- 定时任务系统并发执行多个作业

### 但并发不是免费午餐

它也会带来：

- 共享状态复杂度
- 同步成本
- 调试困难
- 数据竞争、死锁、饥饿等问题

所以更准确的说法是：

> 我们需要并发，不是因为它“更高级”，而是因为它能提升吞吐、响应性和资源利用率；但必须接受更高的正确性和调试成本。

### 面试回答要点

> 并发的主要价值在于隐藏等待、提升吞吐和响应性，以及利用多核能力；但它会引入共享状态和时序复杂度，因此应只在确有收益时使用。

## 2 什么是竞争条件（Race Condition）？请举例说明。

竞争条件是指：

> 程序结果依赖于多个线程 / goroutine / 进程之间的执行时序，而这种时序又不可控。

最典型的情况是多个执行单元同时读写共享变量，而没有正确同步。

### 经典例子

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    count := 0
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            count++
        }()
    }

    wg.Wait()
    fmt.Println(count)
}
```

直觉上结果应该是 `1000`，但实际可能小于 `1000`。

### 为什么会这样

`count++` 并不是一个不可分割的原子操作，它通常包括：

1. 读 `count`
2. 加 `1`
3. 写回 `count`

如果两个 goroutine 同时执行这三步，中间发生交错，就会丢失更新。

### 如何解决

#### 1. 加锁

```go
var mu sync.Mutex
mu.Lock()
count++
mu.Unlock()
```

#### 2. 原子操作

```go
atomic.AddInt64(&count, 1)
```

#### 3. 避免共享可变状态

例如通过 channel 串行化更新。

### 面试回答要点

> 竞争条件的本质是共享可变状态遇上不可控时序。只要存在 read-modify-write 且缺少同步，就很容易出现 race。解决思路通常是加锁、原子操作，或者从设计上消除共享状态。

## 3 什么是死锁（Deadlock）？请写一个导致死锁的例子。

死锁是指：

> 两个或多个执行单元彼此等待对方释放资源，导致谁都无法继续推进。

### 一个典型例子

```go
package main

import (
    "sync"
)

var muA sync.Mutex
var muB sync.Mutex

func main() {
    var wg sync.WaitGroup
    wg.Add(2)

    go func() {
        defer wg.Done()
        muA.Lock()
        defer muA.Unlock()

        muB.Lock()
        defer muB.Unlock()
    }()

    go func() {
        defer wg.Done()
        muB.Lock()
        defer muB.Unlock()

        muA.Lock()
        defer muA.Unlock()
    }()

    wg.Wait()
}
```

### 死锁是怎么发生的

可能出现这种顺序：

- goroutine 1 先拿到 `muA`
- goroutine 2 先拿到 `muB`
- goroutine 1 等 `muB`
- goroutine 2 等 `muA`

双方互等，程序卡死。

### 死锁常见必要条件

经典 Coffman 条件包括：

- 互斥
- 占有且等待
- 不可抢占
- 循环等待

### 如何避免

#### 1. 统一加锁顺序

例如永远先拿 `muA` 再拿 `muB`。

#### 2. 减少锁嵌套

锁持有时间越短越好。

#### 3. 使用超时、try-lock 或上下文取消

避免无界等待。

#### 4. 从设计上减少共享资源争用

例如 actor 模型、channel 串行化、任务分片。

### 面试回答要点

> 死锁的核心是循环等待资源。工程上最常见的预防手段是固定锁顺序、减少锁嵌套、缩短临界区，以及尽量减少共享状态。

## 4 什么是饥饿（Starvation）？

饥饿是指：

> 某个线程 / 任务虽然理论上可以继续执行，但长期拿不到所需资源或调度机会，导致迟迟无法推进。

它和死锁不同：

- **死锁**：大家都卡住了
- **饥饿**：系统整体可能还在运行，但某些任务一直被“饿着”

### 常见原因

- 不公平锁
- 调度器长期偏向某些任务
- 高优先级任务长期抢占低优先级任务
- 读锁长期压制写锁
- 重试风暴导致某些请求永远抢不到资源

### 一个现实例子

如果一个系统不断有高优先级请求进入，低优先级后台任务可能一直得不到 CPU 或数据库连接，虽然系统没有死锁，但后台任务可能永远做不完。

### 如何缓解

- 使用公平调度策略
- 设置优先级老化（aging）
- 限流，避免热点请求占满全部资源
- 为不同任务池隔离线程 / 连接池
- 控制重试和退避策略

### 面试回答要点

> 饥饿不是互相等待，而是某些任务长期得不到执行机会。它在高竞争、高优先级抢占和资源池设计不当时很常见，解决思路通常是公平性、隔离和限流。

## 5 什么是 Wait-Free 算法？它和 Lock-Free、Obstruction-Free 有什么区别？

这些概念都属于 **非阻塞同步（non-blocking synchronization）** 范畴。

### 为什么需要非阻塞同步

传统阻塞同步（如 mutex、semaphore）虽然常用，但可能带来：

- 死锁
- 优先级反转
- 长时间阻塞
- 上下文切换开销

所以在某些高性能并发场景下，会考虑无锁 / 非阻塞算法。

### Wait-Free

**Wait-Free** 的定义是：

> 每个线程的每个操作都能在有限步内完成，不依赖其他线程的执行速度。

这意味着它对每个线程都提供了最强的进度保证。

### Lock-Free

**Lock-Free** 的定义是：

> 在任意时刻，系统中总有至少一个线程能在有限步内取得进展。

它保证系统整体在前进，但不保证每个线程都不会饥饿。

### Obstruction-Free

**Obstruction-Free** 的定义是：

> 如果一个线程在没有竞争的情况下单独运行，它能在有限步内完成操作。

这是三者中最弱的保证。

### 关系总结

可以理解为：

- Wait-Free ⇒ Lock-Free
- Lock-Free ⇒ Obstruction-Free

### 为什么 Wait-Free 很少见

因为它实现复杂、代价高，而且常常需要：

- 更复杂的算法设计
- 更高的内存开销
- 对硬件原子指令能力的高度依赖

现实工程中更常见的是：

- mutex
- RWMutex
- CAS + lock-free 结构
- channel / actor / queue

### 面试回答要点

> Wait-Free 提供最强的每线程进度保证，Lock-Free 保证系统整体前进，Obstruction-Free 只保证无竞争时能完成。现实工程里 Wait-Free 很少见，更多见的是锁、CAS 和较弱但更实用的非阻塞结构。

## 6 为什么测试多线程或并发程序很困难？

因为并发 bug 往往不是“逻辑错了”，而是：

> 只会在某种特定时序下才暴露，而这个时序往往不稳定、难复现、对环境敏感。

### 难点在哪里

#### 1. 执行顺序非确定

线程调度受到很多因素影响：

- CPU 核数
- 调度器策略
- 系统负载
- 时钟中断
- I/O 时机

同一段代码多跑几次，行为可能不同。

#### 2. 竞争条件很隐蔽

代码在测试机上可能“永远没问题”，但在生产高负载下突然出现丢数据、重复写、状态错乱。

#### 3. 死锁和饥饿难稳定复现

它们高度依赖时序和资源竞争状态。

#### 4. Heisenbug 问题

加日志、开调试器、放慢程序，可能反而让 bug 消失。

### 怎么提高测试有效性

#### 1. 尽量减少共享可变状态

这是最根本的办法。

#### 2. 使用竞态检测工具

例如：

- Go `-race`
- ThreadSanitizer
- Java 并发测试工具与 profiler

#### 3. 做压力测试和长时间 soak test

放大时序问题暴露概率。

#### 4. 设计可控调度点

在关键位置插入 hook、barrier 或 test double，强制制造特定交错顺序。

#### 5. 加强可观测性

并发问题排查往往需要：

- 线程 dump
- tracing
- 锁等待指标
- 队列长度
- 重试次数
- goroutine profile

### 面试回答要点

> 并发测试困难的根源是时序非确定性。很多 bug 只有在特定交错顺序下才出现，所以除了单元测试，还需要 race detector、压力测试、可观测性和尽量减少共享状态的设计策略。
